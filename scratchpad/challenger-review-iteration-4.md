## Verdicts (headline)

1. **`training-execution-service` is being scaffolded with a known, already-solved authentication gap — this is a new, avoidable regression, not a repeat of an old, forgivable one.** ADR-008's aggregate sketch defers auth to "an ADR-007-equivalent... once this service has its own," but ADR-007 already exists, is already proven in production against the same `identity-service`, and unlike when `exercise-service`/`training-planning-service` were first built (before `identity-service` issued real tokens), that blocker is gone. See §1.
2. **The client-submits-the-snapshot decision is sound as the *primary* mechanism, but "the same trust boundary as ADR-003, not a new one" overstates the parallel** — and the gap that framing papers over collides directly with ADR-004's non-retroactive-recompute guarantee, turning an unverified snapshot into a source of *permanent* incorrect derived facts, not just a transient UX inconvenience. The "sync a verified copy in the background when online" alternative is real, cheap, and under-weighed, not overkill. See §2.
3. **`Forma.Executor` is a real naming risk, cheap to fix now and expensive after the rename script runs.** "Executor" is heavily overloaded with a generic, unrelated technical meaning in exactly this codebase's own ecosystem (task/thread/job executors). See §3.
4. **The per-set rest override (rule 1) is the right call on the merits, but it's treated with less caution than a smaller override in the same section (rule 4)** — inconsistent, worth closing the loop with the product owner. See §4.

## 1. `training-execution-service` scaffolded without auth from day one — an unforced regression

ADR-008's aggregate sketch says the `OwnerId` field will be "enforced per an ADR-007-equivalent authentication pattern **once this service has its own**." Read plainly, this means the new service's first real build-out ships with the exact same gap `ADR-006`/`integration-patterns.md`'s security note already flagged system-wide and `ADR-007` already spent real effort closing for the other two services: any caller can act on any `WorkoutSession`, for any user, with the caller's identity unverified.

The difference that matters: when `exercise-service` and `training-planning-service` were first built with a caller-supplied `RequestingUserId` stand-in (`Forma.Exercise/docs/features/FT-001-ownership-visibility.md`), that was a genuinely reasonable sequencing call — `identity-service` wasn't issuing real tokens yet, so there was nothing to validate against. That blocker is gone now. `ADR-007` is Accepted, working, and describes a directly reusable pattern (HS256, shared secret with `identity-service`'s `fastapi-users` `JWTStrategy`, `sub`/`aud` claim validation, no shared assembly). `training-execution-service` is the *first* of the four services being built from scratch after that pattern already exists in this codebase. Deferring auth "until this service has its own ADR-007-equivalent" isn't closing a pre-existing gap the way ADR-007 did — it's *opening a new one*, on a brand-new service, for no reason grounded in a real constraint (unlike the original two services' excuse).

This also isn't a low-stakes surface. `WorkoutSession` data is a user's live, personal training activity — at least as sensitive as the Exercise/Workout data ADR-007 already protects, and per `domain-model.md`, potentially carrying attached Media Resources (e.g. a video of the user performing the session) that are considerably more sensitive than a shared Exercise library entry.

**Recommendation**: the next pass on `training-execution-service` should treat wiring in ADR-007's pattern from day one as part of this service's *initial* build, not a follow-up gap to retrofit later — the same way `exercise-service`/`training-planning-service` had to retrofit it, at real cost, once `identity-service` became real. There is no equivalent excuse this time.

## 2. Client-submitted snapshot: right primary mechanism, overstated trust-boundary analogy, under-weighed alternative

**What's right**: rejecting a synchronous `training-execution-service → training-planning-service` call as the *primary* session-start mechanism is well-argued, and sharper than a rote reapplication of ADR-006's pattern. The key insight — "there is nothing to fail open *to*" — correctly distinguishes this case from ADR-006 Rule 1, where a Dangling Reference is an accepted, gracefully-degraded fallback. Here, the fetched data doesn't validate an otherwise-well-formed request; it *is* the data. Combined with ADR-003's offline-start requirement, building a synchronous fetch as the primary path really would mean maintaining two divergent code paths with a real risk of pinning different Workout Versions depending on network timing at the exact moment "start" is pressed. Agreed: don't do that.

**What's overstated**: `integration-patterns.md` justifies zero server-side verification by claiming this is "the same trust boundary this project has already accepted for this exact aggregate," citing ADR-003's acceptance of unverified, potentially out-of-order client-submitted set-by-set results. That parallel doesn't fully hold. ADR-003's actual-performance data (reps, weight, duration actually done) has **no authoritative source other than the client** — the user's own report of what they did *is* the only fact that could ever exist. The Workout Version snapshot is categorically different: it's a copy of something that **does** have an authoritative source of truth, sitting right there in `training-planning-service`, that the system is simply choosing never to check against, ever, even asynchronously, even when fully online. Treating "the client is authoritative for its own experience" and "the client is authoritative for a copy of someone else's stored record" as the same kind of trust is the actual premise being smuggled through unchallenged.

**Why this specific gap matters more than a typical stale-cache race**: `ADR-004` already commits this project to *not retroactively recomputing* Progress Tracking / Progress Analytics values once derived. If a stale or corrupted client-submitted snapshot misattributes a session's sets to the wrong Exercise, or pins content that never matched any real `WorkoutVersion` `training-planning-service` ever issued, the resulting bad PR/volume/trend data becomes a **permanent** fact by design — not a recoverable UX inconvenience the way a Dangling Reference is (rule 1's whole justification for tolerating it). And the likely failure mode here isn't malicious tampering (ADR-001's single-user model, no adversarial multi-party stakes) — it's exactly the kind of mundane bug this project's own architecture makes *more* likely than usual: ADR-003 already requires the client to carry and rely on locally cached state for offline operation, which by construction raises the odds of a stale-cache session-start relative to a typical always-online app. `integration-patterns.md`'s own dismissal — "nothing today identifies a concrete problem this would solve" — isn't accurate; the concrete problem is this ADR-004 interaction, already established elsewhere in this same document set, not a hypothetical to wait on "if evidence ever surfaces."

**On the specific question asked**: is "sync a verified copy in the background when online, but let it start immediately either way" a real alternative, or overkill? **Real, and currently under-weighed, not overkill.** It doesn't reintroduce the two-divergent-paths problem (session start is still always client-submitted, uniformly, online or offline) — it adds a strictly non-blocking, best-effort background job that fires *after* the session already started, only when connectivity allows, whose only job is to flag (not correct, not block) a submitted snapshot that doesn't match any `WorkoutVersion` `training-planning-service` actually has on record. Given ADR-004 already establishes that a session can be edited after the fact, a flagged mismatch has a real, already-legitimate remediation path (a human or a future tool corrects the session, future — not past — Progress Tracking computations then reflect the fix).

**Recommendation**: don't block scaffolding on this, but don't leave it framed as "no concrete problem, revisit only if evidence surfaces" either. At minimum, name the ADR-004 interaction explicitly as the reason this is worth a cheap, non-blocking, log-only reconciliation job from early on — this is the same shape of recommendation Iteration 2's review made for ADR-006's fail-open silence (`challenger-review-iteration-2.md` §2): an accepted trust boundary is fine, but an accepted trust boundary with **zero observability** into how often it's actually being violated is a much bigger, silent risk than the same boundary with a cheap log line attached.

## 3. `Forma.Executor` — a real naming collision, not a stylistic quibble

ADR-008 frames the name choice as "low-stakes and easily overridden," but the word itself carries a specific, heavily-used technical meaning in exactly the ecosystem this project already works in: "Executor"/"IExecutor"/"ExecutorService"-style names are the standard vocabulary for generic task/thread/job execution infrastructure (the .NET TPL, Hangfire-style background job runners, the Java `ExecutorService` lineage many .NET engineers also carry intuitions from). A developer scanning `Forma.Resource/` for the first time, seeing `Forma.Auth`, `Forma.Planner`, `Forma.Executor` sitting next to each other, has every reason to guess the third one is shared cross-cutting infrastructure (a generic command/job runner) rather than "the service that owns live workout-session execution" — exactly the opposite of what `Forma.Auth`/`Forma.Planner` communicate unambiguously about their own bounded contexts. This is a materially worse collision risk than either existing precedent: "Auth" and "Planner" are domain-flavored words that read correctly in context; "Executor" is a term of art for something else entirely, in the same language/runtime this project is written in.

The ADR itself surfaces (without adopting) the better-fitting alternative: `Forma.Session`, named after the aggregate root (`WorkoutSession`) the same way `Forma.Exercise` — this project's own original, standalone precedent — is named directly after its aggregate root, not a role-noun. Counting precedents literally, `Forma.Auth`/`Forma.Planner` are role-nouns and `Forma.Exercise` is an aggregate-root name, so there's no unanimous existing convention either way — the tie-break shouldn't be "which pattern has two examples instead of one," it should be "which name avoids an actual collision with something the codebase's own ecosystem already means by that word." `Forma.Session` clears that bar; `Forma.Executor` does not.

**Recommendation**: rename to `Forma.Session` (or another aggregate/domain-specific alternative — `Forma.Live`, `Forma.Workout Session`-style options were not evaluated in the ADR) before running `Rename_2.ps1`. This is exactly the kind of decision that's nearly free to change today and considerably more annoying once it's baked into a repo name, namespace tree, CI job names, and git history.

## 4. Per-set rest stepping vs. the product owner's own words — right call, inconsistently flagged

Rule 1 (`requirements-and-open-items.md` → Iteration 4) explicitly overrides the product owner's literal dictation ("finish an exercise, rest, move to the next exercise") in favor of per-set stepping. On the merits, this override is correct and not scope creep: the product owner's shorthand, read literally, is flatly incompatible with two things already decided before this iteration — `CLAUDE.md`'s own worked multi-set example (four individually-logged sets with different rep counts) and ADR-003's plural "set-by-set... data actually done." There is no way to log four sets' worth of individually-varying actual reps/weight during one undifferentiated continuous active block; the override isn't an elective enhancement, it's a precondition for the feature being buildable at all consistent with what's already accepted. Rest reusing the single per-entry value (rather than inventing new granularity) is also the right amount of restraint — it resolves the domain model's long-open per-exercise-vs-per-set rest question using data that already exists, rather than adding a new attribute.

**What's inconsistent**: rule 4 (extending rest is UI-only) gets an explicit "Recommend the product owner explicitly confirm this rather than let it stand purely on this document's default" — appropriately, since `requirements-and-open-items.md` itself calls it "the closest-to-arbitrary call in this pass." Rule 1 gets no equivalent call-out, despite **directly contradicting the product owner's own dictated words**, not merely filling a silent gap the way rule 4 does. The reasoning for rule 1 is sound enough that I wouldn't expect the product owner to reject it — but "we're confident you didn't mean this literally" is exactly the kind of inference that should be surfaced back to the person who said it, not just recorded as resolved. This is a paperwork-level finding, not a substance one: the *decision* is fine, the *lack of an explicit confirmation loop* on a decision that overrides the product owner's own words is the gap.

**Recommendation**: no design change — just extend the same "recommend explicit product-owner confirmation" treatment already given to rule 4 to rule 1 as well, next time this document is touched.

## 5. Single rest value applied uniformly, intra-entry and inter-entry — a real v1 gap, one layer deeper than what's already flagged

`domain-model.md` → Workout, "Rest granularity" states the single per-entry rest value "applies uniformly between consecutive sets of that entry, and again as the transition into the next entry in sequence." The document already flags one consequence of this simplification (warm-up-vs-working-set rest, under "Open"). There's a second, more common consequence that isn't named anywhere: most real training experiences distinguish rest **within** an exercise (recovering between sets of the same movement) from rest **between** exercises (which, in a real gym, often needs to be longer — walking to different equipment, adjusting a different station, mental reset for a different movement pattern). Collapsing both into one planned value per entry is a legitimate v1 simplification consistent with "avoid premature complexity" — but it's the kind of thing the very first real user of this feature will notice immediately (a live rest timer that's identical whether the next action is "same exercise, next set" or "totally different exercise, new equipment"), which is a different risk profile than a data-model gap nobody will notice for months.

**Recommendation**: not a design change — just have the next Analyst pass state this explicitly as a **named, known v1 limitation** (the way rule 4's rest-adherence gap and the warm-up-set gap already are), rather than leaving it implied only by the word "uniformly" in a sentence about something else. Costs nothing to write down now; costs a "wait, didn't we think about this?" moment later if it isn't.

## 6. Forma.Resource housing three of four services — deployment independence not confirmed either way

`ADR-005` justifies four independently deployable services partly on paper: `bounded-contexts.md`'s domain-area mapping. Placing `identity-service`, `training-planning-service`, and now (proposed) `training-execution-service` all as subfolders of one `Forma.Resource` monorepo, versus `exercise-service`'s standalone `Forma.Exercise` repo, doesn't automatically violate that independence — but it isn't automatically preserved either, and nothing in `ADR-008` or `context-map.md` confirms one way or the other whether each `Forma.Resource` subfolder has its own independent build/CI/deploy pipeline, or whether they share a root-level solution/pipeline that would couple their build and release cadence even though the code itself stays logically separate. This wasn't verifiable by inspection in the time this review had (no root-level `.sln`/CI config was checked exhaustively). Flagged, not asserted as a problem.

**Recommendation**: before scaffolding a third subfolder into `Forma.Resource`, have whoever runs that scaffolding confirm explicitly (a one-line note in the new service's own `README.md` is enough) that its build/test/deploy pipeline is independent of `Forma.Auth`'s and `Forma.Planner`'s — cheap to confirm now, and it's exactly the kind of assumption that's easy to silently let slip as "just another folder in the same repo" without anyone deciding it that way on purpose.

## Minor / meta observations (not blocking)

- **RavenDB's rationale partly rests on a factor the same document says isn't a commitment.** ADR-008 names "built-in Map/Reduce indexes... a plausible foundation for future Progress Analytics" as one of "two further grounds" that tipped the decision away from MongoDB, then separately states this is "not a commitment... over-committing its design here... would be exactly the premature complexity `CLAUDE.md` warns against." Both statements are honest on their own, but together they mean part of the product owner's actual deciding factor was explicitly non-binding and could evaporate once Progress Analytics is designed for real. The decision still stands on the surviving factor (.NET-native ecosystem fit for an all-.NET project), which is a real, non-speculative benefit on its own — this is a note for future context, not a reason to revisit the (explicitly out-of-scope) choice itself.
- **A repeating pattern worth naming, not stopping**: the product owner has now twice made a major architecture call directly, ahead of the normal Analyst→Architect→Challenger cycle (ADR-005's microservices call, ADR-008's datastore pick) — both explicitly self-labeled as such by the Architect. Nothing wrong with either individual instance, and the process explicitly allows it, but two-for-two on the biggest, most expensive-to-reverse decisions in the project bypassing the "understand the domain before choosing technology" sequencing `CLAUDE.md` otherwise asks for is worth someone keeping half an eye on, purely as a trend.

## What holds up well

- Rejecting a synchronous session-start fetch as the *primary* mechanism — the "nothing to fail open to" reasoning is sharper than a rote reapplication of ADR-006's pattern, and correctly identifies the two-divergent-paths risk a naive "sync when online, client-submit when offline" split would create.
- The per-set live-execution stepping resolution (rule 1) — right outcome, logically required by prior decisions, not elective scope growth (see §4 for the one process gap, not a substance objection).
- "Completed" vs. "Ended Early" as two legitimate, permanent outcomes — directly resolves a real, long-open item, matches `vision.md`'s stated commitment to capturing partial reality, and adds no new domain concept.
- Deliberately leaving Superset/Circuit stepping, whole-entry skip, multi-day pause/resume, Dangling-Reference-in-snapshot interaction, and actual-rest-duration capture all explicitly open rather than speculatively designed now — consistently good "avoid premature complexity" discipline across both the Analyst and the Architect this iteration.
- Rejecting Elasticsearch as a system-of-record store, and rejecting a shared datastore with `training-planning-service` — both well-reasoned on the merits, even though the RavenDB-vs-MongoDB choice itself is out of scope for this review.
- Reusing the `Forma.Resource/Template_DDD` scaffold for a third service, rather than treating `Forma.Exercise`'s standalone layout as an unbreakable rule — a reasonable read of the actual precedent (see §6 for the one open follow-up on this).
- Careful "Accepted" vs. "Proposed, pending Challenger review" status discipline across this pass's new documents — ADR-008's datastore decision (product-owner-made) is clearly separated from its own aggregate sketch and repo-name recommendation (this Architect's own proposals, explicitly not elevated to the same status). Good hygiene, makes this review easier to scope correctly.

## Simplifications / recommendations for next iteration

1. Wire `training-execution-service` into ADR-007's already-proven JWT pattern from its first real build, not deferred to "once this service has its own" equivalent — no remaining excuse for the deferral that justified it the first two times (§1).
2. Add an explicit, cheap, non-blocking reconciliation/log-only check for client-submitted Workout Version snapshots once online — not to block or verify session start, only to make an already-accepted trust boundary observable, given its interaction with ADR-004's permanence guarantee (§2).
3. Rename the proposed service from `Forma.Executor` to `Forma.Session` (or another domain/aggregate-flavored alternative) before running the rename script (§3).
4. Extend the same "recommend explicit product-owner confirmation" note already given to rule 4 (extending rest) to rule 1 (per-set stepping) — the decision is right, the confirmation loop is currently asymmetric (§4).
5. Name the intra-entry-vs-inter-entry uniform-rest simplification as an explicit known v1 limitation, not just an implication of the word "uniformly" (§5).
6. Confirm (one line, in the new service's own `README.md`) that its build/CI/deploy pipeline is independent of `Forma.Auth`'s and `Forma.Planner`'s before scaffolding it into `Forma.Resource` (§6).
