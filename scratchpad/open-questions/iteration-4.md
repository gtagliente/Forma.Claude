# Open Questions — Iteration 4

Surfaced by Challenger review of `ADR-008-training-execution-service-datastore.md`, `integration-patterns.md` → "Session-start Workout Version fetch mechanism", and the Analyst's "Live Workout Session Execution (Iteration 4)" section (see `../challenger-review-iteration-4.md` for full reasoning). Unresolved as of this pass — for the next Analyst/Architect iteration or human product-owner input.

## High priority (affects whether ADR-008 / the integration-patterns.md addendum should be accepted as-is)

1. **`training-execution-service`'s aggregate sketch defers authentication to "once this service has its own ADR-007-equivalent" — should it instead wire in ADR-007's already-proven pattern from its first real build?** Unlike `exercise-service`/`training-planning-service`'s original caller-supplied-id stand-in (built before `identity-service` issued real tokens), this new service is being built *after* a working, reusable auth pattern already exists in this codebase. Shipping it without auth from day one is a fresh, avoidable gap, not a repeat of an old, excusable one — and `WorkoutSession` data (including attached Media Resources) is at least as sensitive as what ADR-007 already protects. See challenger review §1.
2. **Should a lightweight, non-blocking, best-effort background check of the client-submitted Workout Version snapshot (fired only when connectivity is available) be added now, given its interaction with ADR-004's non-retroactive-recompute guarantee?** A stale or corrupted snapshot doesn't just cause a recoverable UX hiccup the way a Dangling Reference does — because Progress Tracking values derived from it are never retroactively recomputed, a bad snapshot becomes a *permanent* incorrect fact. `integration-patterns.md`'s current framing ("no concrete problem identified... revisit if evidence surfaces") understates a risk this document set has already established elsewhere. Not proposing full verification or blocking session start — proposing at minimum an observability signal (log/flag mismatches) so the trust boundary being accepted is at least visible, not silent. See challenger review §2.
3. **Should `Forma.Executor` be renamed before `Rename_2.ps1` runs?** "Executor" collides with a generic, heavily-used technical term (task/thread/job execution infrastructure) in exactly this project's own ecosystem, in a way `Forma.Auth`/`Forma.Planner` don't collide with anything. `Forma.Session` (aggregate-root style, matching `Forma.Exercise`'s own precedent) is a concrete, low-cost alternative already named in the ADR but not adopted. Cheap to change now; expensive once the repo/namespace/CI names are live. See challenger review §3.

## Medium priority (shapes how cleanly this scales / how it lands with the product owner)

4. **Should rule 1's per-set live-execution stepping (which explicitly overrides the product owner's own literal dictated description) get the same "recommend explicit product-owner confirmation" treatment already given to rule 4 (extending rest)?** The decision itself is correct and well-justified (required by ADR-003's already-plural set-by-set data and `CLAUDE.md`'s own multi-set example, not elective) — the gap is only that it's recorded as resolved-by-the-document without the same closed-loop confirmation step given to a smaller override in the same section. See challenger review §4.
5. **Should the single per-entry rest value's "applies uniformly whether the next thing is another set of the same exercise or a transition to a new exercise" simplification be named explicitly as a known v1 limitation?** A second, more commonly-noticed consequence beyond the already-flagged warm-up-set scenario: real training usually wants a different (often longer) rest when switching exercises/equipment than when recovering between sets of the same movement. Not a design change for v1 — just a documentation gap likely to surface as a "didn't we think about this?" moment with the first real users. See challenger review §5.
6. **Is each `Forma.Resource` subfolder (`Forma.Auth`, `Forma.Planner`, and prospectively the new service) independently buildable/deployable, or does the monorepo share a root-level solution/pipeline that would couple their release cadence?** Not confirmed either way by this review. Matters because `ADR-005`'s "four independently deployable services" guarantee should hold at the repo/tooling level, not just the logical bounded-context level, and three-of-four services now sitting in one repo is exactly the situation where that could quietly erode without anyone deciding it on purpose. See challenger review §6.
