# training-planning-service — Open Questions

Consolidates (a) still-open central questions relevant to this service, and (b) new implementation-grounded questions surfaced while bootstrapping `Forma.Planner`.

## Carried from central open items (not this service's to decide alone)

1. **Routine scheduling model** — recurring pattern (e.g. "every Monday") vs. calendar dates, or both? (`../../product/requirements-and-open-items.md` → Ambiguities.) **Implementation note**: FT-003 (`Forma.Planner/docs/features/FT-003-routine-create.md`) added a minimal, deliberately provisional `DayOfWeek?` per entry — a lightweight recurring-style hint, not a resolution. Same "provisional default, not an answer" framing as `exercise-service`'s hierarchy cross-visibility default.
2. **Same Exercise appearing more than once in a Workout** — e.g. warm-up set at lower weight, then working sets. Allowed?
3. **Rest time granularity** — per-exercise or per-set?
4. **Session provenance** — must a Workout Session always trace to a Workout (via a Routine or directly), or can it be freestanding/ad hoc? Primarily `training-execution-service`'s call, but shapes how Routine "schedules occurrences of" Workout Session in the domain-model relationship diagram — this service's Architect should stay aware of it.
5. ~~**Inter-service integration pattern**~~ — **Resolved and accepted** (2026-07-12) — `../../architecture/integration-patterns.md`, `../../architecture/adr/ADR-006-cross-service-reference-integrity.md` (`Status: Accepted`). For the two concrete drivers this service is party to:
   - **Workout create/edit → Exercise existence** (this service calls `exercise-service`): synchronous batch check, inline in the same request, **fail-open** (proceeds if the check is inconclusive/unreachable — only a confirmed negative blocks the save). The same lookup, reused at read time with the same fail-open policy, resolves Dangling References gracefully wherever a Workout is later shown.
   - **Exercise delete → Workout reference** (`exercise-service` calls this service): this service must expose a synchronous "does any Workout reference this Exercise ID" endpoint, **fail-closed** from the caller's perspective (if this service is unreachable, `exercise-service` blocks the delete rather than assuming no reference exists) — see `../exercise-service/open-questions.md` #13.
   - `training-execution-service` reading Workout Version data at session-start is a **separate, already-resolved** case (ADR-002/ADR-005's denormalized-copy answer, not a live existence/reference check) — not part of this ADR-006 decision. *How* that fetch happens at session-start is still open but belongs to `training-execution-service`'s own future central-loop pass, not this item.
6. **New, surfaced while designing item 5's mechanism**: does "referenced by a Workout" (for the delete-block check) mean only the Workout's **current** version, or any historical `WorkoutVersion` too? Provisional default recorded in `../../architecture/integration-patterns.md` (current-version-only) — not a resolution, flagged back to the Analyst/product owner for confirmation. Matters for how this service's reference-check endpoint queries `WorkoutVersion` history once built.

## New, surfaced while bootstrapping this service (service-loop scope)

7. ~~**Workout aggregate boundary**~~ — **Resolved**: single aggregate with an embedded `WorkoutVersion` child-entity history (Option A). See `architecture.md` and `Forma.Planner/docs/features/FT-001-workout-create.md` (Design section).
8. **Stray `IExerciseWriteOnlyRepository.cs`** in `Forma.Planner/src/Forma.Planner.CoreInfrastructure/Abstractions/` — a leftover copied from `exercise-service`'s scaffold, not genericized. **Functionally superseded** by the real `IWorkoutWriteOnlyRepository` (built for FT-001) but the dead file itself is still present — an attempt to delete it during FT-001 was blocked by this environment's auto-mode guard (pre-existing file, not explicitly named by the user for deletion). Safe to delete whenever a human confirms it.
9. **Fixed while implementing FT-001**: `ServicesCollectionExtensions.DbMigrationAssemblyName` was still hardcoded to the pre-rename `"Forma.PublicApi"` after the solution rename to `Forma.Planner` — a real runtime bug (the app would have failed to find its migrations assembly at startup), not just a migration-tooling annoyance. Fixed.
10. **`.sln` references a nonexistent `Forma.UnitTests` project** — same pre-existing scaffold defect `exercise-service` has; build individual `.csproj` files, not the `.sln`, until someone fixes or removes the reference.
11. **`tests/Forma.IntegrationTests` doesn't compile, beyond the no-Docker gap** — `Forma.IntegrationTests.csproj`'s `ProjectReference` still pointed at the pre-rename `Forma.PublicApi.csproj` (never updated even in the original `Forma → Forma.Resource` rename, let alone this pass's `Forma.Resource → Forma.Planner` one) — fixed. But the test files themselves (`ExercisesControllerTests.cs`, and Exercise-specific imports in `AssertExtensions.cs`) are leftover `exercise-service`-shaped scaffold that references domain types (`CreateExerciseCommand`, `ExerciseId`, etc.) that don't exist in this Workout/Routine service at all — still doesn't compile. Not fixed: rewriting these into real Workout/Routine integration tests is new test-authoring work, not something this pass's three Create features asked for. `Forma.ArchitectureTests` is unaffected (separate project, builds and passes).
12. **Workout write-side contract gaps, surfaced by `web-client`'s cross-service client review** (`Workout_React` FT-003, Central Architect Gate, 2026-07-12): the `Workouts` API only exposes `create`, `getall`, `addnewversion` — no update, no delete, no get-by-id, no version-history endpoint. Separately, `addnewversion`'s `403` response has no schema (`content: {"application/json": {}}`, unlike 400/404/500 which all reference `ApiResponse`), so a caller can only branch on status code, never parse a message out of it. Neither gap blocked `web-client`'s wiring (it already works around both — full-list `getall` + client-side index instead of get-by-id, a fixed client-side message for the schema-less 403) — flagged here as this service's own backlog to triage, not a merge blocker. See `Workout_React/docs/features/FT-003-workout-wiring.md` Design section for full detail.
13. **`dayOfWeek` enum ordering unconfirmed**, surfaced by the same review (`Workout_React` FT-004): `RoutineEntryDto.dayOfWeek`/`RoutineEntryQueryModel.dayOfWeek` is documented only as a nullable int, no enum values given. `web-client`'s `CreateRoutineForm.tsx` assumes .NET's `System.DayOfWeek` (Sunday=0..Saturday=6) and has already shipped that assumption into its day-picker option values (approved to merge — CORS is still unconfigured, so nothing has exercised this against a live backend yet, which is the only reason this hasn't already produced wrong data). If the actual enum differs, every day-of-week a user picks will be silently mislabeled once CORS is fixed and the client starts calling this for real. Recommend this service's Service Analyst/Architect confirm the intended ordering explicitly (in `domain.md`/`api-contracts.md` once written) before or immediately after CORS unblocks real end-to-end testing. See `Workout_React/docs/features/FT-004-routine-wiring.md` Design section.
