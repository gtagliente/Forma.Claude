# web-client — Open Questions

First written while bootstrapping this service entry (see `README.md`), when real API wiring was blocked everywhere. Superseded below — `identity-service` went from placeholder to real (`Forma.Auth`) since then, which resolved most of what was blocking. Updated once FT-001 (auth) started moving through `Workout_React`'s own pipeline.

## Resolved since the first pass

1. ~~No `api-contracts.md` for any service~~ — still true as a *formal artifact* (per `../README.md`'s current-state note, none of the three implemented services have written one up yet), but each service's generated/hand-authored `openapi.json` (`exercise-service`: `Forma.Exercise/docs/engineering/openapi.json`; `training-planning-service`: `Forma.Planner/docs/engineering/openapi.json`; `identity-service`: `Forma.Auth/openapi.json`) is being treated as the de facto contract by `Workout_React`'s Frontend Architect — a real generated spec, not reverse-engineered controller code, judged close enough to satisfy that role's "no guessing" gate. See `Workout_React/docs/features/FT-001-auth.md`'s Design section for the explicit reasoning. **Central Architect Gate note, 2026-07-12**: all four of FT-001–FT-004 used this pattern (a fourth consecutive design depending directly on an `openapi.json`); judged still fine to leave `api-contracts.md` deferred rather than prompting a backfill now — the exception is well-justified and consistently applied, and none of the four designs found the openapi.json ambiguous or insufficient. Worth each of the three services picking up as a low-priority documentation task (mechanical, generated from the already-existing spec) so future designs don't keep re-justifying the same exception, but not urgent enough to block or delay feature work for.
2. ~~`identity-service` has no implementation~~ — resolved. It's `Forma.Auth` (Python/FastAPI, `fastapi-users`), with real login/register/logout/`users/me` endpoints. `Workout_React`'s FT-001 is wiring the client against it now.
3. ~~No auth/session model decided for the client~~ — resolved locally by FT-001's design (token in `localStorage`, a shared `authFetch` wrapper, React Context for current-user state) — see that file, not repeated here.

## Still open

4. **`training-execution-service` has no implementation** — Workout Session (performing/logging a workout) still can't be wired.
5. **Cross-service JWT validation doesn't exist yet.** `exercise-service` and `training-planning-service` don't validate a real token from `identity-service` — they still take a caller-supplied `ownerId`/`requestingUserId` at face value (see `identity-service/open-questions.md` #9). This is explicitly planned backend work ("integrate JWT on all endpoints," per the human product owner), not yet done. Until it lands, `web-client` sending the logged-in user's real ID as `ownerId`/`requestingUserId` is meaningful (it's what those services expect today) but not actually verified server-side — anyone could claim any ID by calling the API directly. Not a client-side problem to solve; flagging so it isn't mistaken for already-secure once the client starts doing this. **Update, 2026-07-12**: FT-001–FT-004 all cleared Central Architect Gate and ship real client code that depends on this permissive behavior for the first time (not just a documented future risk) — see `../identity-service/open-questions.md`'s Status note. Still not a client-side problem to solve, and CORS being unconfigured means nothing is actually exercising this end-to-end yet, but the backend fix is now closer to load-bearing than before.
6. **No CORS configured on any of the three backends** for a browser client to call them from the Vite dev server. Blocks actually running/testing `web-client` against live services locally. Backend-repo config, out of `web-client`'s own scope to fix.
7. **No refresh-token endpoint** on `identity-service` — a session's only recovery from token expiry is re-login. `Workout_React`'s FT-001 design accounts for this; noting it here too since it's a property of the contract, not just a local implementation choice.

## Status

Actively narrowing — FT-001 (auth) is the first feature moving through `Workout_React`'s pipeline, unblocked by identity-service going real. Exercise/Workout/Routine CRUD+search features are next, reusing FT-001's token-attachment pattern.

**2026-07-12**: FT-001 (auth), FT-002 (exercise wiring), FT-003 (workout wiring), FT-004 (routine wiring) all cleared their local pipelines and Central Architect Gate — see each file's `## Central Architect Gate` section in `Workout_React/docs/features/`. `web-client` now has real create/list/search wiring against all three backend services behind a real login. New service-specific findings from that review are recorded in `../training-planning-service/open-questions.md` (items 12–13), not duplicated here.
