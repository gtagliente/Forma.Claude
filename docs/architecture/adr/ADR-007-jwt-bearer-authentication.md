# ADR-007: JWT Bearer Authentication for `exercise-service` and `training-planning-service`

## Status

**Accepted** (2026-07-13, Challenger-reviewed, product-owner sign-off given as-is).

## Context

- `identity-service` (`Forma.Resource/Forma.Auth`) already issues real bearer tokens today via `fastapi-users`' `JWTStrategy(secret=SECRET, lifetime_seconds=3600)` (`app/users.py`). By inspection of that library's default behavior: HS256 (HMAC, symmetric — already decided by the product owner, not revisited here), payload claims `sub` (the user's UUID as a string), `aud` (defaults to `["fastapi-users:auth"]`, not overridden here), `exp` — and **no `iss` claim** (fastapi-users' default `generate_jwt` never sets one).
- `exercise-service` and `training-planning-service` were built with a caller-supplied `RequestingUserId`/`OwnerId` standing in for real auth, explicitly flagged for replacement once `identity-service` existed (`Forma.Exercise/docs/features/FT-001-ownership-visibility.md` → "Auth stand-in"; mirrored by `training-planning-service`'s `CreateWorkoutCommand.OwnerId` / `AddWorkoutVersionCommand.OwnerId` / `CreateRoutineCommand.OwnerId`).
- `requirements-and-open-items.md` → "Authenticated request identity (Iteration 3)" resolves the business rule this ADR closes: every operation touching a user's own data must act on a validated identity, never a caller-asserted id; this enforces ADR-001's already-decided ownership model, it does not extend it (no roles, no delegation, Identity stays the minimal `User` in `bounded-contexts.md`).
- This is a security boundary independently implemented, identically, by two services against one external issuer and one shared secret — the same "same-shape decision, consumed by two services" situation ADR-006 already set precedent for, and squarely inside this repo's ADR bar (`README.md`: "touch security... or cross-service APIs").

## Decision

**1. Both services add ASP.NET Core JWT Bearer authentication, each independently configured to the same values (no shared assembly between them — the same configuration recipe, applied twice, since ADR-005 keeps them independent deployables):**

| Setting | Value | Why |
|---|---|---|
| Algorithm / key | HMAC-SHA256, `SymmetricSecurityKey` from a shared-secret **configuration** value (e.g. `Auth:JwtSigningKey`) | Matches `identity-service`'s `JWTStrategy`; sourced from config (appsettings/env/secret manager), not hardcoded outside a documented dev default — the current real dev value is `sakjdhkjad872323`, confirmed by the product owner, rotated later without a code change |
| `ValidateIssuerSigningKey` | `true` | Standard |
| `ValidateIssuer` | `false` | `identity-service` emits no `iss` claim at all — validating one that never exists would fail every token |
| `ValidateAudience` / `ValidAudience` | `true` / `"fastapi-users:auth"` | `fastapi-users`' documented default `token_audience`, not overridden by `identity-service` |
| `ValidateLifetime` | `true` | Respects `exp` (3600s from issuance) |
| `MapInboundClaims` | `false` | Keep the raw `sub` claim as issued rather than ASP.NET Core's legacy remap to a `ClaimTypes.NameIdentifier` URI — both services standardize on reading the literal `sub` claim as the user id |

**2. A new `ICurrentUserAccessor` abstraction** (neither codebase has an equivalent today — confirmed by inspection) wraps `IHttpContextAccessor` (already registered in both `Program.cs`), exposing `Guid? UserId` (parsed from `sub`) and `IsAuthenticated`. Controllers and MediatR command/query handlers use it; nothing reads `ClaimsPrincipal` directly. Same interface shape recommended in both services (not literally shared code).

**3. Ownership/visibility enforcement layered on top of authentication — this, not the middleware alone, is what actually closes FT-001's gap:**

- Any create/edit/delete of a user's own data requires `[Authorize]`. The acting user's id always comes from `ICurrentUserAccessor`, never a client-supplied field — `OwnerId`/`RequestingUserId`-shaped command/query properties stop being bindable from the request (`[JsonIgnore]` or equivalent) and are populated by the controller after model binding, per FT-001's own anticipated replacement ("replace the explicit parameter with a value derived from the request's authenticated principal"), not merely defaulted-but-overridable.
- **`exercise-service`**: `Exercise` keeps its shared/private duality (`OwnerId` nullable). `GetAll`/`GetById` stay anonymous-accessible (point 4, below). A create request signals "shared vs. mine" via a non-identity-bearing flag (e.g. a `Shared` bool), never by asserting an arbitrary `OwnerId`. `Update`/`Delete` — which today have **no ownership check at all** (confirmed by reading `UpdateExerciseCommandHandler`/`DeleteExerciseCommandHandler`: neither the command nor the handler reference an owner/requesting user in any way) — gain a Forbidden-on-mismatch check for private Exercises, mirroring the pattern already established elsewhere in this project (below). This is a pre-existing gap this ADR closes, not a new one it introduces.
- **`training-planning-service`**: `Workout`/`Routine` have no shared-library concept — every operation is "mine" data, so **every** endpoint (`Create`, `GetAll`, `AddNewVersion`, and any future `Update`/`Delete`/`GetById`) requires `[Authorize]`, with no anonymous path at all (unlike `exercise-service`). `AddWorkoutVersionCommandHandler` already contains `if (workout.OwnerId != request.OwnerId) return Result.Forbidden();` — today this check is cosmetic (any caller can simply assert the matching `OwnerId` and pass it), because `OwnerId` is caller-supplied. This ADR is what makes that existing check actually secure, by making `OwnerId` server-derived instead.

**4. Anonymous shared-library reads (Analyst open question 2): resolved as anonymous-allowed, `exercise-service` only.** `GetAll`/`GetById` do not require `[Authorize]`; an absent or invalid token degrades to the shared-library-only view rather than a 401 — never a data leak (nothing private is reachable without a matching validated identity), and no spurious error on an endpoint that never depended on identity in the first place. `training-planning-service` has no equivalent case — every Workout/Routine belongs to exactly one user, so there is no "shared" view to expose anonymously; nothing to open there.

## Alternatives considered

- **RSA/JWKS discovery** — out of scope; already decided against by the product owner (see task framing). Not revisited.
- **A shared auth library/NuGet package between the two services** — rejected. The services are independent deployables (ADR-005) with no shared-code precedent today; the validation configuration is a handful of `TokenValidationParameters` values, cheap enough to duplicate correctly twice per this document, without standing up shared-package infrastructure. Revisit only if a third .NET consumer of `identity-service` tokens appears and the configuration is observed to drift.
- **Require authentication on every `exercise-service` read too** (uniform with `training-planning-service`) — rejected per the Analyst's own recommendation: nothing justifies gating a pure shared-library browse behind an account; doing so anyway is exactly the unnecessary complexity `CLAUDE.md` warns against.
- **Keep `OwnerId`/`RequestingUserId` client-supplied but cross-checked against the token when present ("soft" validation)** — rejected. This keeps the impersonation vector alive for any caller who simply supplies a value; FT-001 already anticipated full replacement of the parameter, not a soft check layered on top of it.

## Consequences

- Both services take a new runtime dependency on holding the correct shared secret; a misconfigured/mismatched secret between `identity-service` and either consumer fails all authenticated operations closed — the safe failure direction for a security control (contrast with ADR-006's availability-oriented fail-open/fail-closed split, which is about a different kind of risk).
- Closes a real, pre-existing authorization gap, independent of this iteration's stated trigger: `UpdateExerciseCommand`/`DeleteExerciseCommand` (`exercise-service`) had no ownership enforcement before this ADR; `AddWorkoutVersionCommand` (`training-planning-service`) had a check that looked like enforcement but wasn't (caller-suppliable `OwnerId`).
- `GetExerciseByIdQuery` is annotated in code as backing both the public `GetById` surface and, once built, ADR-006 Rule 1's cross-service Exercise-existence check. Adding end-user visibility scoping to it now means that future ADR-006 endpoint **must not** blindly reuse this same handler — that check's trust boundary is the *calling service*, not a particular end-user's visibility. Flagged here for whoever builds that endpoint, so it isn't discovered as a bug later.
- **Not addressed by this ADR, flagged as a known follow-up**: the ADR-006 internal service-to-service endpoints (`exercise-service`'s equivalent of `training-planning-service`'s `ExerciseReferencesController.IsReferenced`) are still explicitly unauthenticated (`integration-patterns.md` → "Security note" already flagged this as deferred "until `identity-service` moves past placeholder status"). `identity-service` is no longer a placeholder as of this ADR — closing that gap is a real, near-term follow-up, but it is a *different* problem (service-to-service credentials, not end-user bearer tokens) and is not solved here.
- **The shared secret's real-world storage risk is not fully covered by "sourced from config, rotated later without a code change."** Verified against the actual codebases (Challenger, see review below): `Forma.Auth/app/users.py` already hardcodes `SECRET = "sakjdhkjad872323"` directly in committed Python source (not env/secret-manager), and both `exercise-service`'s and `training-planning-service`'s existing `appsettings.Development.json` already commit equally sensitive values in plaintext (DB password, Redis password, `CacheOptions`). Given that established, repo-wide convention, the dev JWT secret will very likely land the same way in both consuming services' checked-in `appsettings.Development.json` too — three git-tracked repos holding the identical plaintext secret, not a hypothetical. This is an acceptable *dev*-environment risk consistent with existing project convention, not a reason to block this ADR, but "rotated later without a code change" should not be read as "already safe" — production deployment must source the secret from an actual secret store/env var and must never reuse the dev value, and that should be an explicit, tracked follow-up, not assumed implicit in this line.
- No change to `bounded-contexts.md`'s Identity context (still a minimal `User`, no roles/delegation) — this ADR enforces ADR-001's existing ownership model; it does not extend it.

## Challenger review (Iteration 3)

Verdict: **no blocking issues found; the ADR is sound and ready to be presented for product-owner sign-off**, with one Consequences addition made above (secret storage risk) and the notes below for awareness — none of them change the Decision.

Claims independently verified against code (not taken on the Architect's restatement alone):

- `UpdateExerciseCommandHandler`/`DeleteExerciseCommandHandler` (`Forma.Exercise/src/Forma.Application/Exercise/Handlers/`) — confirmed: neither references an owner/requesting-user id anywhere; the "no ownership check today" claim is accurate, and this ADR genuinely closes a real pre-existing gap, not a rhetorical one.
- `AddWorkoutVersionCommandHandler` (`Forma.Resource/Forma.Planner/src/Forma.Planner.Application/Workout/Handlers/`) — confirmed: `if (workout.OwnerId != request.OwnerId) return Result.Forbidden();` exists exactly as described, and is indeed only cosmetic today since `request.OwnerId` is caller-supplied and unvalidated.
- `Forma.Auth/app/users.py` — confirmed HS256 (`JWTStrategy(secret=SECRET, lifetime_seconds=3600)`), no `iss` claim emitted, default `aud` (`fastapi-users` default `"fastapi-users:auth"`, not overridden), 3600s lifetime. ADR's restatement is accurate.
- `exercise-service`'s current `GetVisibleToAsync`/`GetAllExerciseQueryHandler` anonymous-read path (`Forma.Exercise/src/Forma.Query/...`) — confirmed the visibility filter is `OwnerId == null OR OwnerId == requestingUserId`, and the cache key is scoped per-`requestingUserId`. For today's actual anonymous case this degrades correctly to shared-only, no leak. The residual point worth naming for whoever implements `ICurrentUserAccessor`: it must represent "anonymous" as `null`, not `Guid.Empty` or another default `Guid` — if a future refactor accidentally coalesces "no token" to a real-looking `Guid`, the same `OR` filter shape would silently start returning nobody's-and-everybody's private data as if it were shared. Not a defect today; worth one sentence in whoever's implementation notes, not a reason to hold this ADR.
- Anonymous access on `exercise-service` reads does not, on today's code, reopen anything FT-001 already closed — but it does slightly change the blast radius *if* a future filtering bug is introduced: under uniform authentication (as `training-planning-service` has), a broken filter is still exploitable, but only by someone willing to hold an account; with `exercise-service`'s anonymous reads, the same future bug would be exploitable by literally any network caller, no account needed. This doesn't argue against the anonymous-read decision itself (the Analyst's business case for it stands, and blocking all reads behind an account has no product justification) — it's a reason to treat "the visibility filter on every anonymous-accessible query" as a slightly higher-bar-for-review code path going forward, not a reason to require auth for shared-library browsing.
- The ADR-006 service-to-service auth gap: agree this is honestly scoped as "flagged, not solved" and shouldn't block this ADR's sign-off — it's explicitly a different problem (service credentials, not end-user tokens) that was already flagged before this ADR existed (`integration-patterns.md` → "Security note"). One point worth naming explicitly, though: before ADR-007 ships, an unauthenticated caller reaching *any* endpoint on these services was normal — the gap was uniform. After ADR-007 ships, the ADR-006 endpoints become the **only** remaining unauthenticated door into either service. That doesn't make the decision to defer wrong, but it does raise the follow-up's priority from "known gap, revisit eventually" to "the next thing that should get picked up," and whoever owns that follow-up should not let it sit indefinitely just because it was pre-existing.
- "No shared assembly, duplicate the recipe" — agree, no pushback. Two consumers, a handful of config values, consistent with ADR-005's independent-deployables stance and the same reasoning already accepted for the ADR-006 client-generation default (`integration-patterns.md` → "Central mandate or per-service default?"). Revisit only if a third .NET consumer appears or the two copies are observed to drift.
- `ICurrentUserAccessor` and the `Shared` boolean flag — proportionate, not over-engineering. Both replace an existing insecure mechanism (raw `ClaimsPrincipal` reads scattered around / a caller-suppliable `OwnerId`) with a narrow, single-purpose abstraction; neither introduces speculative generality (no roles, no policy engine, no multi-tenancy).
- Cross-checked against `requirements-and-open-items.md`'s two open questions for this iteration (token/failure-handling mechanism; whether shared-library reads stay anonymous) — both are answered by this ADR (points 1 and 4 of the Decision) in a way traceable back to the Analyst's own framing; nothing was decided that the Analyst left open on purpose.
